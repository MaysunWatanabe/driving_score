===============================================================================
 BLE 車載機（DrivingCanData）エミュレータ  ble-can-emulator.py
===============================================================================

開発機（Linux）を BLE ペリフェラルとして動作させ、アプリが期待する車載機に
なりすまして 12 バイトの CAN パケットを notify する検証用ツール。

実車・実車載機が無くても、アプリの BLE 受信経路（スキャン → 接続 → notify →
デコード）を実機の Android 端末で検証できる。

-------------------------------------------------------------------------------
 1. これは何で、何ではないか
-------------------------------------------------------------------------------

これは:
  開発 PC が「本物の車載機のふり」をして、実機の Android アプリと
  本物の BLE 接続を確立し、CAN データを流し込むツール。
  アプリから見て本物の車載機と区別がつかないことが要件。

これではない:
  ui.edit.page から sensor-log をアップロードして DemoData で再生する方式。
  あちらはアプリ内でのファイル再生であり、BLE スタックを一切通らない。
  両者は目的が異なる。

  ┌─────────────────┬──────────────────────┬────────────────────────┐
  │                 │ 本ツール             │ DemoData 方式          │
  ├─────────────────┼──────────────────────┼────────────────────────┤
  │ BLE スタック    │ 通る（実接続）       │ 通らない               │
  │ 必要な機材      │ 開発 PC + 実機 2 台  │ 1 台（ブラウザでも可） │
  │ 検証できるもの  │ BLE 経路そのもの     │ スコアロジック / UI    │
  └─────────────────┴──────────────────────┴────────────────────────┘


 1-1. エミュレータは 2 系統ある（proposal #16）

このリポジトリには同じ目的のエミュレータが 2 つある。**既定は本ツール（A）**。

  A（既定）  src/data/tools/ble-can-emulator.py        ← 本ファイルが説明するもの
  B（代替）  src/tools/ble-can-emulator/               ← 既存。凍結扱い

  ┌───────────────┬────────────────────────┬──────────────────────────┐
  │               │ A（本ツール・既定）    │ B（代替・フォールバック）│
  ├───────────────┼────────────────────────┼──────────────────────────┤
  │ BT スタック   │ BlueZ の D-Bus API     │ bumble を HCI に直結     │
  │ 追加依存      │ なし（OS 同梱のみ）    │ bumble（venv に pip）    │
  │ 実行権限      │ sudo 不要              │ 要 sudo                  │
  │ BlueZ         │ 動かしたまま共存       │ mask + stop して占有     │
  │ 送出データ    │ mock/*.txt.gz の再生   │ math.sin の合成波        │
  │ Phase 1 判定  │ こちらで行う           │ 対象外・未検証           │
  └───────────────┴────────────────────────┴──────────────────────────┘

B に切り替えてよいのは、A が使えない次の場合だけ:
  - BlueZ が org.bluez.LEAdvertisingManager1 を提供しない
  - bluetoothctl show の SupportedInstances が 0
  - A の RegisterAdvertisement / RegisterApplication が失敗する

 ★ 相互排他（MANDATORY）

  A と B は同時に起動できない。B は bluetoothd を止めて HCI を占有するため、
  B の稼働中は A が使う D-Bus API そのものが消える。

  B を使ったあと A に戻すときは、必ず先に BlueZ を復帰させること:

      sudo src/tools/ble-can-emulator/restore-bluez.sh

  B の run.sh は SIGKILL・ターミナル強制終了で trap が発火せず、
  bluetooth.service が masked のまま残る。mask は永続設定なので、
  この状態は **再起動しても直らない**。A が「BlueZ に接続できない」と
  言い出したら、まず上記スクリプトを実行して復帰させること。

  B のファイル（driving_can_peripheral.py / run.sh / restore-bluez.sh 等）は
  凍結扱いで、削除・リファクタ・機能追加をしてはならない（proposal #16）。

 2. 動作要件
-------------------------------------------------------------------------------

開発 PC 側:
  - Linux のみ（Windows / macOS は非対応。proposal #14 / #15 の非適用範囲）
  - Python 3（標準ライブラリのみ使用）
  - python3-dbus
  - PyGObject（gi.repository.GLib）
  - BlueZ 5.72 以降（org.bluez.LEAdvertisingManager1 / GattManager1）
  - Bluetooth アダプタが peripheral ロールに対応していること
      確認: hciconfig -a  →  "Link mode:" に PERIPHERAL が含まれること
  - 広告のアドレスタイプが public であること（→ §8 の status 0x3E を参照）
      確認: bluetoothctl show  →  1 行目が "Controller XX:.. (public)"
            /etc/bluetooth/main.conf の Privacy が off（既定）であること

  新規の pip / apt パッケージは追加しない（proposal #14 / #15 で禁止）。

  検証済み環境:
      Python 3.12.3 / dbus 1.3.2 / BlueZ 5.72
      hci0 = Realtek BT 5.3、Link mode に PERIPHERAL / Roles: central, peripheral

実機（Android）側:
  - 本アプリがインストールされていること
  - Bluetooth が有効であること
  - 位置情報が有効であること（GPS は全モードで起動時ゲートの必須条件。proposal #28）
  - 設定「利用するセンサー情報」が「車載BLEのみ」または「併用」であること
      ※ 「端末センサーのみ」(smartphoneOnly) では BLE 接続処理自体がスキップされるため、
        エミュレータを起動しても永久に接続されない。最頻出のハマりどころ。
      ※ commit 09bc238 以降、canDataOnly では端末を振る必要がなくなった（下記）。


-------------------------------------------------------------------------------
 3. 使い方
-------------------------------------------------------------------------------

作業ディレクトリは src/data。

  # Phase 1: 接続確立の疎通確認（proposal #15 §3 が定める疎通用シナリオ）
  python3 tools/ble-can-emulator.py \
      --source mock/sensor-log.cruise.canConnected.txt.gz

  # 実時間 60 秒で 1 トリップ（出車 → 走行 → 駐車）を流し切る。
  # 駐車行動 D→R→P を含むためスコアが算出される（proposal #32）。

  # 別シナリオを送出（急ブレーキ）
  # ※ 正準シナリオは 1 トリップで完結するため --loop を付けない（proposal #32）
  python3 tools/ble-can-emulator.py \
      --source mock/sensor-log.hard_brake.canConnected.txt.gz

  # 送信周期を変える（既定 100ms）
  python3 tools/ble-can-emulator.py \
      --source mock/sensor-log.mixed.canConnected.txt.gz --rate-ms 50 --loop

停止は Ctrl-C。

オプション:

  --source PATH     [必須] 入力にする sensor-log.<scenario>.canConnected.txt.gz
                    canData を持たない smartphoneOnly の生成物は拒否される。

  --rate-ms N       notify 送信周期 [ms]。既定 100、範囲 10〜1000。
                    ※ この 100ms は暫定値である。実車載機の実 notify 周期は
                      仕様・fact に記載が無く、判明した時点で差し替える前提
                      （proposal #14 §4）。

  --loop            入力の末尾に達したら先頭へ戻って送出を続ける。
                    指定しない場合、集約後の 600 フレーム（既定 100ms なら 60 秒）で
                    送出を終えて待機状態になる。

                    ★ 正準シナリオでは使わないこと（proposal #32）。
                      各シナリオは P で始まり P で終わる 1 トリップとして完結する。
                      途中から繰り返すと P→D→…→P の整合が崩れ、駐車行動の
                      検知がおかしくなる。1 周 60 秒で終わるので --loop は不要。

  --raw             集約せず 1 レコード = 1 notify で送出する（proposal #25）。
                    モックは 10ms 刻みなので再生が 1/10 速度になり、
                    6000 レコードの送出に約 10 分かかる。
                    送出値がモックの canData と 1 対 1 対応するため、
                    バイト単位の突き合わせ検証に使う。

  --adapter NAME    使用する Bluetooth アダプタ名（既定: hci0）。
                    ※ BLE 契約・送出データに影響しない実行上の補助オプション。

  --verbose         送出フレームの表示を 10 件ごとに増やす（既定は 100 件ごと）。
                    proposal #60 の裁定で、毎フレーム表示（rate-ms=100 で毎秒
                    40 行）から 10 件ごと（毎秒 4 行）に落としている。
                    ※ 同上。

典型的な出力:

  [source] mock/sensor-log.cruise.canConnected.txt.gz
  [source] 6000 レコードを 10 件ずつ集約し 600 フレームに符号化しました（先頭: 28 80 80 64 80 2a 30 28 00 00 04 00）
  [source] 実時間 60.0 秒で送出します（600 件 × 100ms）
  [adapter] /org/bluez/hci0
  [ready] 実機アプリで診断を開始してください。
  [ready] settings.selectedSensorMode は canDataOnly / combination のいずれかにすること。
  [ready] 停止は Ctrl-C。
  [gatt] service 00002310-0000-1000-8000-00805f9b34fb / characteristic 00002311-... を公開しました
  [adv] LocalName=DrivingCanData で広告を開始しました
  [notify] 購読開始（アプリが startNotifications を呼びました）
  [send] #000001 28 80 80 64 80 2a 30 28 00 00 04 00
     speed   40 km/h | longAcc +0.00 G | latAcc +0.00 G
     front  50.0 m   | lateral +0.0 m | steer +0.0 deg
     accel   40 %    | brake    0 bar | bSw 0(OFF) shift 4(D) turn 0(OFF)

  1 行目は送出した 12 バイトそのもの（logcat との突き合わせ用）。2〜4 行目は
  その 12 バイトを infra.ble.device のデコード式で復号した物理量で、単位・列挙
  ラベルは設計書由来（proposal #60）。符号化前の canData ではなく実際に送出する
  バイト列を復号しているため、クランプ・量子化の結果がそのまま見える。

  列挙ラベル:
    brakeSwitch      0:OFF 1:ON
    shiftIndication  1:P 2:R 3:N 4:D 6:L 7:B
    turnSignal       0:OFF 1:L 2:R 3:HAZ
  定義に無い値は shift 5(?) のように (?) を表示するだけで、エラーにも警告にも
  せず送出は継続する（エミュレータは入力を忠実に送る役割であるため）。


-------------------------------------------------------------------------------
 4. BLE 仕様（アプリ側の期待値。変更してはならない）
-------------------------------------------------------------------------------

  広告 LocalName          DrivingCanData
                          アプリは result.device.name の「完全一致」でのみ
                          識別する。1 文字でも違うと永久に検出されない。

  Primary Service UUID    00002310-0000-1000-8000-00805f9b34fb
  Notify Characteristic   00002311-0000-1000-8000-00805f9b34fb
  Characteristic プロパティ  notify のみ

  MAC アドレス            固定しない。アプリに BLE_DEVICE_ID 定数はあるが
                          実装上未使用で、識別は名前のみで行われる。

アプリ側の接続フロー:

  1. BleClient.initialize() → isEnabled() → requestLEScan({services: []})
     ※ サービス UUID では絞らず、名前で選別している
  2. 3 秒後にスキャン停止
       0 件   → 「Bluetooth接続に失敗しました。」ダイアログ（リトライ可）
       1 件   → 自動接続
       複数件 → ラジオ選択ダイアログ
  3. 念のため disconnect してから connect(timeout: 10000)
  4. discoverServices でサービス探索の完了を待つ（proposal #18 で追加）
     ※ connect は探索完了前に解決しうる。Android は接続確立時に MTU 交換を
       自発的に行い、プラグイン 2.3.0 はその onMtuChanged で connect を
       resolve するため。この待機が無いと空の GATT DB に対して
       startNotifications を呼び、Characteristic not found で必ず失敗する。
  5. startNotifications で購読開始 → 12 バイトをそのままデコードへ渡す

  接続に失敗した場合は disconnect してから「Bluetooth接続に失敗しました。」
  ダイアログを出す（proposal #18）。切断せずに残すとペリフェラルが広告を
  再開せず、再スキャンで検出できなくなる。

  → エミュレータが起動していない状態で診断を始めると、3 秒後に
    「Bluetooth接続に失敗しました。」が出る。先にエミュレータを起動しておくこと。


-------------------------------------------------------------------------------
 5. 12 バイトパケットの仕様
-------------------------------------------------------------------------------

固定長 12 バイト。offset 5-6 のみ u16 ビッグエンディアン（他は u8）。

  off  型      物理量               アプリ側デコード      エミュレータ側エンコード
  ---  ------  -------------------  --------------------  --------------------------
   0   u8      vehicleSpeed         v * 1                 round(v)
   1   u8      longAcc              v * 0.01 - 1.28       round((v + 1.28) / 0.01)
   2   u8      latAcc               v * 0.01 - 1.28       round((v + 1.28) / 0.01)
   3   u8      frontDistance        v * 0.5               round(v / 0.5)
   4   u8      lateralDistance      v * 0.5 - 64          round((v + 64) / 0.5)
  5-6  u16 BE  steeringAngle        v * 0.1 - 1080        round((v + 1080) / 0.1)
   7   u8      accelPedalPosition   v * 1                 round(v)
   8   u8      brakePressure        v * 1                 round(v)
   9   u8      brakeSwitch          そのまま              そのまま
  10   u8      shiftIndication      そのまま              そのまま
  11   u8      turnSignal           そのまま              そのまま

  ・各フィールドは u8 (0..255) / u16 (0..65535) の表現域にクランプする。
  ・round は「.5 を上へ」。Python 組込み round() は偶数丸めなので使わず、
    floor(x + 0.5) で実装している（モックログ側の JS Math.round と揃えるため）。

手検算の例（cruise の 1 レコード目）:

  28 80 80 64 80 2a 30 28 00 00 04 00
  │  │  │  │  │  └─┬─┘ │  │  │  │  └─ turnSignal        = 0
  │  │  │  │  │    │    │  │  │  └──── shiftIndication   = 4 (D レンジ)
  │  │  │  │  │    │    │  │  └─────── brakeSwitch       = 0
  │  │  │  │  │    │    │  └────────── brakePressure     = 0
  │  │  │  │  │    │    └───────────── accelPedal        = 0x28 = 40
  │  │  │  │  │    └────────────────── steeringAngle     = 0x2a30=10800 → 0.0 deg
  │  │  │  │  └─────────────────────── lateralDistance   = 0x80=128 → 0.0 m
  │  │  │  └────────────────────────── frontDistance     = 0x64=100 → 50.0 m
  │  │  └───────────────────────────── latAcc            = 0x80=128 → 0.00 G
  │  └──────────────────────────────── longAcc           = 0x80=128 → 0.00 G
  └─────────────────────────────────── vehicleSpeed      = 0x28 = 40 km/h


-------------------------------------------------------------------------------
 5-1. 10 レコード集約（proposal #25 / #26）
-------------------------------------------------------------------------------

モックログは 10ms 刻み、車載機の notify は 100ms 間隔。この差を埋めるため、
既定では 10 レコードを 1 フレームへ集約してから送出する。

  6000 レコード（モック時間 60 秒） → 600 フレーム → 実時間 60 秒

集約しないと 1 レコードを 100ms かけて送ることになり、再生が 1/10 速度になる
（60 秒のシナリオに実時間 10 分）。実際、集約導入前の実機検証では 77 秒流しても
モック時間で 7.7 秒ぶんしか届かず、hard_brake の制動イベント（12 秒地点）に
到達しなかった。

 フィールド別の集約規則

  平均を取る（proposal #25 の 5 つ + #26 の steeringAngle）
    vehicleSpeed / longAcc / latAcc / frontDistance / lateralDistance / steeringAngle

    設計書はこのうち steeringAngle を除く 5 つに「※平均値」と付記している。
    steeringAngle は付記が無いが、区間先頭を採ると実質デシメーションになり
    #25 の「間引きはピーク取りこぼしのため不採用」に反するため平均とした（#26）。

  区間先頭を採る
    accelPedalPosition / brakePressure          … proposal #26
    brakeSwitch / shiftIndication / turnSignal  … proposal #25

    前者 2 つは proposal #13 §4 の 3 状態規則により 40 / 100 / 0 / 126 の
    離散値しか取らない。区間が状態遷移をまたぐと平均は規則に存在しない
    中間値（例 70）を生むため、先頭値を採る。brakeSwitch と連動させる意味もある。
    後者 3 つは列挙値なので平均できない。

  平均後の丸めは floor(x + 0.5)（.5 を上へ）。偶数丸めは使わない。
  末尾が 10 で割り切れない場合、残り全部で平均を取る（切り捨てない）。

 ★ --rate-ms との関係

  集約数は 10 固定で、--rate-ms とは連動しない（#25 / #26 が 10 固定として決定）。
  --rate-ms 50 を指定すると 100ms ぶんのデータを 50ms で送ることになり、
  再生が 2 倍速になる。実車と同じ時間軸で流したい場合は既定の 100 を使うこと。

 実測（集約後、2026-08-20）

  シナリオ      speed      longAcc        steering        pedal        brake
  cruise        40         0.00           0.0             [40]         [0]
  hard_brake    11〜60     -0.47〜+0.35   0.0             [0,40,100]   [0,126]
  sharp_curve   40         0.00           -179.8〜+179.8  [40]         [0]
  mixed         0〜60      -0.47〜+0.35   -179.8〜+179.8   [0,40,100]   [0,126]

  pedal / brake に中間値が出ていないこと、制動のピーク（-0.47G）が
  集約後も残っていることを確認済み。steeringAngle は平均によりピークが
  ±180.0 から ±179.8 へわずかに鈍る。

 7. Phase 1（BLE 接続確立）の完了ゲート  ★ 2026-08-19 に completed
-------------------------------------------------------------------------------

★ Phase 1 は proposal #20 (synced) により **completed** と確定した。
  判定は proposal #16 のとおり実装 A のみで行い、実装 B は検証対象外のまま凍結。
  実測値は §10「検証済み（実機 2026-08-19）」を参照。
  以下は再検証したい場合の手順として残す。

proposal #15 が定める完了条件。以下 4 点がすべて成立したとき Phase 1 完了。

  (a) 開発 PC が LocalName=DrivingCanData で LE 広告を出している
  (b) 実機アプリの 3 秒スキャンで当該デバイスが 1 件検出され、自動接続に進む
  (c) connect(timeout:10000) が成功し startNotifications が確立する
  (d) characteristic 00002311-... の 12 バイト値が実機に到達していることを
      logcat で実測確認できる

  ※ 「運転診断が回ること」「スコアが変化すること」は完了条件に含まれない。

    理由（当時）: アプリのセンサー集約は GPS・加速度・ジャイロ・磁力の 4 つが
    揃うまで毎 tick 即 return していた。ジャイロは deviceorientationabsolute
    由来で、端末を静置していると通知が飛んでこない。つまり BLE が完璧でも、机に
    置いたままでは診断が回らなかった。BLE 経路の成否と診断の成否を同じゲートに
    載せると切り分けができなくなるため、意図的に分けている。
    （このゲートは proposal #28 で改訂された。下記の※を参照）

  ※ 起動時ゲートは proposal #28 で selectedSensorMode 別に改訂された
    （commit 09bc238）。上記の「静置だと診断が回らない」は canDataOnly には
    もう当てはまらない。

      canDataOnly    : GPS + canData
      smartphoneOnly : GPS + 加速度計 + 方位 + 磁力計
      combination    : 両方

    GPS が全モード必須なのは、地図表示・ヒヤリ地点の座標・車両マーカーの向きに
    要るため。向きは geolocation.heading を使う（driving.page.ts:452）ので、
    deviceorientationabsolute を別途ゲートする必要はない。

    ゲート対象外のセンサーは構造を保ったゼロ値で埋める（proposal #30）。
    acceleration.interval は 10 とする。0 にすると SensorManager の
    calibrationTotalTime が閾値 1100 に到達せず、キャリブレーションが永久に
    完了しないため ScoreLogic へ 1 件も積まれない。

    ゲートの性質（tick の skip であること / 起動時に一度だけ作用すること /
    DemoData 経路は通らないこと）は #19 のまま変わらない。

    実測（2026-08-21 / SH-M29 / canDataOnly / hard_brake / 端末は静置）:
      canData 受信 383 件 / 中高速走行 検知 2 回 / ヒヤリ 発生 4 回 /
      pushBadPoint 4 回 / TypeError 等 0 件
    端末を一度も振らずに診断が最後まで動作し、地図上のヒヤリ地点マーカーの
    表示も確認した。

手順:

  1. 開発 PC でエミュレータを起動
       cd src/data
       python3 tools/ble-can-emulator.py \
           --source mock/sensor-log.cruise.canConnected.txt.gz --loop
     → [adv] LocalName=DrivingCanData で広告を開始しました  が出ることを確認 …(a)

  2. 実機の設定で selectedSensorMode を canDataOnly か combination にする

  3. 実機で logcat を流しておく
       adb logcat | grep -i "DrivingScore\|Bluetooth\|Capacitor"

  4. 実機アプリで診断を開始
     → 3 秒スキャン後に自動接続されること …(b)
     → 接続成功と通知購読開始が logcat に出ること …(c)
     → PC 側に [notify] 購読開始 が出る
     → 12 バイトが実機に届いていること …(d)

  5. PC 側の [send] 行に出る 16 進と、logcat のデコード結果を突き合わせる
     cruise なら speed=40 / longAcc=0.00 / latAcc=0.00 / steering=0.0 で一定。

 8. うまくいかないとき
-------------------------------------------------------------------------------

「Bluetooth接続に失敗しました。」が出て検出されない
  - selectedSensorMode が smartphoneOnly のままではないか（最頻出）
  - エミュレータを先に起動しているか（アプリのスキャンは 3 秒で打ち切られる）
  - PC 側に [adv] LocalName=... の行が出ているか
  - 実機の Bluetooth と位置情報権限が有効か

検出はされるが接続が確立しない（GATT status 0x3E）
  ★ 広告のアドレスタイプが public でない可能性が高い。

  Android の @capacitor-community/bluetooth-le は addressType=public 前提で
  接続してくるため、こちらが random static アドレスで広告していると
  GATT 接続の確立が status 0x3E で失敗する。
  （これは既存の bumble 版エミュレータで実際に踏んだ問題。proposal #16 で
    本ツール側の知見として移植した。）

  本ツールはアドレスタイプを明示指定せず BlueZ の既定に従うため、
  次の 2 点を確認すること:

      bluetoothctl show | head -1
        → "Controller XX:XX:XX:XX:XX:XX (public)" と出ること
           (random) と出る場合は public にする必要がある

      grep -n "^Privacy" /etc/bluetooth/main.conf
        → 何も出ない（= コメントアウトされた既定 off）か、
           "Privacy = off" であること。device / network になっていると
           RPA（ランダム化アドレス）で広告してしまう

エミュレータ起動時に登録エラーが出る
  - [ERROR] LE 広告 の登録に失敗 → 他のプロセスが広告枠を使っていないか。
    ActiveInstances / SupportedInstances を確認:
      busctl get-property org.bluez /org/bluez/hci0 \
             org.bluez.LEAdvertisingManager1 ActiveInstances
  - アダプタが peripheral 非対応 → hciconfig -a の Link mode を確認

BlueZ / D-Bus に接続できない、hci0 が見つからない
  - 代替エミュレータ B（src/tools/ble-can-emulator/）を使ったあと、
    bluetooth.service が masked のまま残っていないか。§1-1 の相互排他を参照。
      systemctl is-active bluetooth.service    → inactive なら該当
      systemctl is-enabled bluetooth.service   → masked なら該当
    復帰:
      sudo src/tools/ble-can-emulator/restore-bluez.sh
    mask は永続なので、この状態は再起動しても直らない。

接続はできるが notify が届かない
  - PC 側に [notify] 購読開始 が出ているか。出ていなければアプリが
    startNotifications に到達していない（接続直後で落ちている可能性）

接続直後に logcat へ Characteristic not found が出て失敗する
  ★ proposal #18 の ble.ts 修正が入っていないビルドである可能性が高い。

  commit 1cf7df9 より前のビルドでは connect がサービス探索の完了を待たずに
  解決するため、空の GATT DB に対して startNotifications を呼び、
  writeDescriptor|00002310|00002311|00002902 が Characteristic not found で
  拒否される。探索完了は接続から 800ms 以上かかる一方、アプリは数 ms で
  startNotifications を呼ぶため、構造的に必ず負ける。

  該当ビルドかどうかは logcat で判別できる:
      修正後 … resolve: discoverServices Services discovered. が
               startNotification の前に出る
      修正前 … discoverServices が一度も出ず、
               reject: writeDescriptor|... Characteristic not found が出る

パイプに流すと出力が見えない
  - 行バッファに固定してあるので通常は問題ない。
    `| head` と組み合わせた場合のみ SIGPIPE で切れることがある。
    ログを取るなら `> emu.log 2>&1` か `| tee emu.log` を使う。

診断は始まるがスコアが動かない
  - まず設定「利用するセンサー情報」を確認する。「端末センサーのみ」だと
    BLE 接続自体が走らない。
  - 位置情報が無効だと GPS が埋まらず、全モードで記録が始まらない（proposal #28）。
  - 「端末センサーのみ」「併用」では加速度・方位・磁力も必要。方位
    (deviceorientationabsolute) は静置だと発火しないため、診断開始直後に
    端末を傾ける必要がある。「車載BLEのみ」なら不要。
  - スコアが 100 のまま動かない場合、モックが古い可能性がある。
    proposal #32 以降の正準シナリオは駐車行動 D→R→P を含むため score1 /
    歩行機能 / 認知機能が算出される。node tools/gen-mock-sensorlog.mjs --canonical
    で再生成すること。ヒヤリはスコアを変えない設計
    （scoreLogicFunction.txt の該当箇所にコメントあり）。

 11. Phase 2（異常系）
-------------------------------------------------------------------------------

proposal #20 (synced) により、Phase 2 は **異常系に限定** される。
運転診断の通し E2E・スコア反応・DB 保存・履歴反映は Phase 2 に含まれず、
下記「Phase 2 に含めないもの」の OQ が解消された後の別フェーズで扱う。

対象は次の 4 項目。いずれも未着手。

 (2-1) 切断
   走行中に接続が切れたときのアプリ側の挙動を確認する。
   エミュレータを Ctrl-C で止める、または PC 側から
   `bluetoothctl disconnect <実機アドレス>` で切る。

   ※ 現状、切断後の自動再接続ポリシーは未決（proposal #20 で据え置きが確定）。
     したがって本項目は「どう振る舞うべきか」の判定ではなく
     「実際にどう振る舞うか」の観測に留める。観測結果は propose_decision の
     入力材料とする。

 (2-2) 不正ペイロード
   12 バイト固定長の契約（§5）を破る値を送ったときの挙動を確認する。
   長さ違い（11 / 13 バイト）、全 0x00、全 0xFF など。

   ※ エミュレータ本体に不正値送出機能は無い。本項目の実施には
     ble-can-emulator.py への一時的な改造か専用オプションの追加が必要で、
     それ自体が仕様判断になるため、着手前に propose_decision を通すこと。

 (2-3) rate 境界
   --rate-ms の下限 10 / 上限 1000 の境界値で送出し、取りこぼし率を測る。

   ※ 既定 100ms は proposal #14 §4 / #20 により暫定値のまま据え置き。
     実車載機の実 notify 周期が不明なため、境界測定の結果をもって
     既定値を確定させてはならない。測定値は fact として記録するに留める。

   参考実測（Phase 1 / 2026-08-19、--rate-ms 100）:
     notify 1066 件 / 106.918s / 平均間隔 100.4ms / 取りこぼし 0.39%
     接続間隔は interval=6（7.5ms）にネゴシエートされており、
     10ms notify も物理的には可能と見られるが未測定。

 (2-4) smartphoneOnly 入力拒否の回帰
   canData を持たない sensor-log.cruise.smartphoneOnly.txt.gz を --source に
   指定したとき、終了コード 1 で拒否されることを確認する。

   ※ これは開発 PC 上で完結し、実機を必要としない。§10 の「検証済み（開発 PC 上）」
     に初回実装時の確認結果があるが、回帰として Phase 2 で再確認する。

  - canDataOnly と combination のセンサー購読差の確定（未決のまま据え置き）
