# db.hiyari.model — ヒヤリ事象データモデル

- ノード: `db.hiyari.model`
- エントリポイント: `spec/db/hiyari-model.md`
- ステータス: 凍結解除済み（hiyari テーブル新設を決定）

---

## 1. 目的

診断（運転機能チェック）中に発生したヒヤリ事象を永続化するデータモデルを定義する。
ヒヤリ事象を使う主な機能は次のとおり。

| 用途 | 本モデルとの関係 |
|---|---|
| 1-2 前回結果表示のマップ | 過去のヒヤリポイント（位置）を件数を絞って取得する |
| ホーム画面ウィジェット「今日のヒヤリ / N 件」 | 本日分の件数を取得する |
| 要求⑤「ヒヤリ発生時の録画データサイズ改善」 | 録画ファイルの参照先と、録画内の時刻を保持する |

---

## 2. スコープ

**対象**
- ヒヤリ事象 1 件ごとの記録（hiyari テーブル）
- 日毎件数の算出方法
- 表示件数の上限の扱い
- 上記に必要なインデックス・マイグレーション・整合性ルール

**対象外**
- 録画ファイル本体の形式・圧縮方式・サイズ削減の手法（要求⑤の録画側ノードが担当）
- マップ上のマーカー描画、ウィジェットのレイアウト（UI ノードが担当）
- CAN / BLE ペイロードからヒヤリを判定するロジック（Middleware 側が担当）
- 能力指標の保持（capability_score。別ノードで扱い、6 項目・5 段階化は未確定）

---

## 3. 保存する事実

ヒヤリ事象 1 件につき、次の事実を保存する。

| 事実 | 保存 | 備考 |
|---|---|---|
| どの診断（スコア記録）で発生したか | する | `score_id` |
| いつ発生したか | する | `timestamp` |
| どこで発生したか | する | `latitude` / `longitude` |
| 録画のどの時点に当たるか | する | `video_time` |
| 録画ファイルの場所 | する | `video_path`。ファイル本体は DB に入れない |
| 日毎のヒヤリ件数 | **しない** | 都度 GROUP BY で算出する（§6） |
| 表示件数の上限値 | **しない**（本テーブルには持たない） | 設定値として外部に持つ。呼び出し側で LIMIT に使う（§7） |

---

## 4. テーブル定義: `hiyari`

| 列 | 意味 | 型・単位 | 必須 |
|---|---|---|---|
| `score_id` | ヒヤリが発生した診断（スコア記録）の識別子 | 参照先の識別子型に合わせる（未確定） | 必須とする想定（未確定） |
| `timestamp` | ヒヤリ発生時刻 | 時刻表現と単位（epoch 秒 / ミリ秒 等）は未確定 | 必須 |
| `latitude` | ヒヤリ発生地点の緯度 | 実数（REAL 想定） | 位置未取得時の扱いは未確定 |
| `longitude` | ヒヤリ発生地点の経度 | 実数（REAL 想定） | 同上 |
| `video_time` | 録画内でヒヤリに当たる時刻 | 意味（録画先頭からのオフセットか、絶対時刻か）と単位は未確定 | 未確定 |
| `video_path` | ヒヤリ時の録画ファイルへのパス | 文字列 | 録画が無い場合の扱いは未確定 |

**設計上の注記**
- 承認済みの列は上記 6 列である。行を一意に識別するための代理キー（自動採番 ID 等）の要否は、この設計判断では明示されていない。実装時に確認すること（§13）。
- 型は意味を優先して記載している。既存の `capability_score` が REAL 型を使っていることから、同じ DB（SQLite 系）に置く前提で「REAL 想定」と記載した。ただしこれは前提（assumption）である。
- 録画ファイル本体は DB に格納せず、パスだけを保持する。

---

## 5. 参照関係

```
[診断 / スコア記録] 1 ──── 0..* [hiyari]
        (score_id)
```

- 1 回の診断で、ヒヤリは 0 件以上発生しうる。
- `score_id` の参照先となるテーブル名・キーは、本ノードでは確定していない（§13）。
- `video_path` はファイルシステム上の録画ファイルを参照する。DB の外部キーではないため、DB 側ではファイルが実在することを保証しない。

---

## 6. 導出値: 日毎件数（保存しない）

- 日毎のヒヤリ件数は**保存しない**。取得のたびに `hiyari` を日付単位で GROUP BY して算出する。
- 「日付」は端末ローカル日付で区切る。ウィジェットが端末ローカル日付を基準に「今日のヒヤリ」を扱うため、これと揃える。
- ウィジェットの「本日分の件数」は、この算出結果のうち当日の値を使う。
- 集計値を保存しないため、件数が記録実体とずれることはない。削除・追加の直後でも、再取得すれば正しい値になる。

**クエリ例（概念）**
```sql
-- 端末ローカル日付ごとの件数（timestamp の単位に応じて変換式を調整する）
SELECT <local_date(timestamp)> AS day, COUNT(*) AS cnt
FROM hiyari
GROUP BY day
ORDER BY day DESC;
```

---

## 7. 表示件数の制限（LIMIT）

- 取得件数の上限は設定値で決める。
  - 既定値: **10**
  - 許容範囲: **[1, 100]**
- 上限は DB スキーマに持たない。**呼び出し側がクエリの LIMIT に設定値を渡して絞る**。
- この仕組みは、1-2 のマップがマーカーで埋まることへの対策として使う（背景の open_question「1-2 に表示する過去ヒヤリの件数」）。件数を固定値にせず、設定値にしておく方式である。
- 範囲外の値（0 以下、101 以上）が与えられたときの補正方法、および設定値の保存場所は本ノードの管轄外とし、Middleware 側で決める（§13）。

**クエリ例（概念）**
```sql
-- 直近 N 件のヒヤリ（N は設定値。既定 10、[1,100]）
SELECT score_id, timestamp, latitude, longitude, video_time, video_path
FROM hiyari
ORDER BY timestamp DESC
LIMIT :n;
```

---

## 8. 想定アクセスパターン

| # | 用途 | 条件 | 並び | 件数 |
|---|---|---|---|---|
| A1 | 1-2 マップの過去ヒヤリ | 全件、または対象範囲で絞る | `timestamp` 降順 | LIMIT 設定値 |
| A2 | ウィジェットの本日件数 | 端末ローカル日付 = 本日 | — | COUNT |
| A3 | 日毎件数の一覧 | 全件 | 日付降順 | GROUP BY |
| A4 | 診断単位のヒヤリ取得 | `score_id` = 対象 | `timestamp` 昇順 | 全件 |
| A5 | ヒヤリの追加（診断中） | — | — | 1 件ずつ INSERT |

---

## 9. インデックス

| 名前（案） | 列 | 目的 |
|---|---|---|
| `idx_hiyari_timestamp` | `timestamp` | A1 の降順取得＋LIMIT、A2・A3 の日付範囲絞り込み |
| `idx_hiyari_score_id` | `score_id` | A4 の診断単位取得、参照整合性の確認 |

- 日付の GROUP BY は `timestamp` を式で変換してから行うため、インデックスが効きにくい。件数が多くなった場合は、本日分を取得するときに GROUP BY ではなく「本日 0 時〜翌日 0 時」の範囲条件で `idx_hiyari_timestamp` を使う方法を推奨する。

## 10. 凍結解除（旧 §10「要整理」の解消）

- 以前の版では、本ノードは §10 を「要整理」として凍結していた。
- 次の内容を承認したことで要整理は解消し、**凍結を解除した**。
  1. `hiyari` テーブル（`score_id` / `timestamp` / `latitude` / `longitude` / `video_time` / `video_path`）を新設する。
  2. 日毎件数は保存せず、都度 GROUP BY で算出する。
  3. 表示件数は設定値（既定 10、[1,100]）を使い、呼び出し側の LIMIT で絞る。
- 背景の各事実のうち、次のものは本ノードでは解除していない。
  - スコアロジックの凍結（fact #90 / #94）
  - 能力指標の保持構造の見直し

  本ノードの凍結解除は、ヒヤリ事象の保持に限った話である。

---

## 11. トランザクション・整合性

- ヒヤリの追加は 1 件単位の INSERT とする。複数件をまとめて投入する場合は 1 トランザクションで行い、途中で失敗したときは全件をロールバックする。
- `score_id` の参照先となる診断記録は、ヒヤリの記録より先に（または同じトランザクション内で）存在していること。
- 診断記録を削除したときに `hiyari` の行をどう扱うか（連鎖削除 / 残す）は未確定（§13）。
- `video_path` が指すファイルを削除したときに DB の行をどう扱うかも未確定（§13）。DB 側では、ファイルが実在することを制約として保証しない。
- 日毎件数は導出値なので、集計値との整合を保つための処理は不要。

---

## 12. マイグレーション

- 既存 DB に `hiyari` テーブルを追加する。既存テーブル（`capability_score` 等）の構造は変更しない。
- DB スキーマのバージョンを上げ、アップグレード時に `CREATE TABLE`（存在しない場合のみ）と §9 のインデックス作成を実行する。
- 既存ユーザー向けに移行する過去データは無い。`hiyari` は空の状態から始まる。この場合、ウィジェットは「0 件」と表示する（空状態は「_」ではなく 0 件で表示するという承認済み事実と整合する）。
- ダウングレードは想定しない。

---

## 13. 未確定事項

1. `score_id` の参照先テーブル・キー、および NOT NULL にするかどうか。
2. `timestamp` の時刻表現と単位（epoch 秒 / ミリ秒 / ISO 文字列）。GROUP BY の変換式に影響する。
3. `video_time` の意味（録画先頭からのオフセットか、絶対時刻か）と単位。
4. 位置を取得できなかったとき（`latitude` / `longitude`）、録画が無いとき（`video_path` / `video_time`）の NULL 許容。
5. 代理キー（行 ID）の要否と、一意制約の要否（同じ診断・同じ時刻の重複をどう扱うか）。
6. 診断記録や録画ファイルを削除したときの `hiyari` 行の扱い、および保持期間。
7. 表示件数の設定値の保存場所と、範囲外の値をどう補正するか。
8. 1-2 の過去ヒヤリの抽出範囲（全期間の直近 N 件か、履歴平均の集計期間に合わせるか）。履歴平均の集計期間（現行 30 日）とどう関係させるかは、背景でも未確定である。
9. CAN データを確認用に保存できるかどうか（背景の open_question）。保存する場合、`hiyari` との関連づけが必要になる可能性がある。

---

- 録画（要求⑤）: `video_path` / `video_time` の生成元、ファイルのライフサイクル
- QA: 件数の算出、LIMIT の境界値、空状態、マイグレーションの検証
