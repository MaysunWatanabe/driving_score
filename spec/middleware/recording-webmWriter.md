# middleware.recording.webmWriter — WebM 書き出し仕様

- **ノード**: `middleware.recording.webmWriter`
- **entrypoint**: `spec/middleware/recording-webmWriter.md`
- **ドメイン**: Middleware（録画／ビジネスロジック）
- **関連要求**: 2026 年度改修要求 ⑤「ヒヤリ発生時の録画データサイズ改善」（日産自動車『運転機能チェックアプリの一次仕様』2026-08-04、メイサンソフト『要求仕様確認』2026-09-17）

---

## 1. 目的

録画ストリームを WebM ファイルへ書き出す。
入力は録画元から逐次渡されるチャンク列で、出力は再生可能な WebM ファイルである。
本ノードの責務は次の 3 点に限る。

1. ヘッダのバイト長を固定する。
2. 各チャンクの Cluster Timecode を t0 基準へ振り直す。
3. クローズ時に、確定した Duration をヘッダへ書き戻す。

> 本ノードはチャンクの取得（録画開始・停止のトリガー）、ヒヤリ判定、ファイルの保存先・保持期間を扱わない。これらは呼び出し元ノードの責務である。

## 2. 用語

| 用語 | 意味 |
|---|---|
| ヘッダ | WebM ファイル先頭に置く、Duration を含むヘッダ領域。ファイル位置 0 から書き込む。範囲は §7 Q1 を参照 |
| プレースホルダ | open 時にヘッダへ入れる `Duration=0` の値 |
| チャンク | 録画元から本ノードへ逐次渡されるバイト列 |
| Cluster Timecode | WebM の各 Cluster が持つ基準時刻 |
| t0 | Cluster Timecode を振り直すときの基準時刻。定義は §7 Q2 を参照 |
| 繰り越しバッファ | 各チャンクの末尾 32 バイトを保持し、次のチャンクの先頭へ連結するためのバッファ |

## 3. ライフサイクル

```
open ──▶ write(chunk) × N ──▶ close
```

### 3.1 open

1. ヘッダを出力先の位置 0 に書き込む。このとき Duration には **プレースホルダ `Duration=0`** を入れる。
2. プレースホルダを入れる目的は、**ヘッダのバイト長を open 時点で固定すること**である。
3. 繰り越しバッファは空の状態で開始する。

### 3.2 write（チャンクごとの処理）

各チャンクは、**書き込む前に**次の処理を行う。

1. 前回から繰り越した末尾 32 バイトを、今回のチャンクの先頭に連結する。
2. 連結したデータに含まれる **Cluster Timecode を t0 基準へ振り直す**。
3. 連結したデータの **末尾 32 バイトは書き込まず**、繰り越しバッファへ移す。
4. 残りを出力先へ追記する。

処理順序の制約は次のとおり。

- Timecode の振り直しは、そのチャンクを書き込む前に完了していなければならない。書き込んだ後に遡って修正する処理は行わない。
- 末尾 32 バイトは、次のチャンクと連結されるまで出力しない。

### 3.3 close

1. （前提・要確認）繰り越しバッファに残っている末尾バイトに振り直し処理を行い、出力先へ追記する。
2. 録画の Duration を確定する。
3. **確定した Duration を持ち、open 時と同じバイト長のヘッダ**を、出力先の **位置 0 に上書き**する。
4. 出力先を閉じる。

> 手順 1 は、繰り越し方式の性質上必要と考えられる手順である。ただし承認済み fact には明記されていないため、前提として扱う（§7 Q5）。

## 4. 不変条件

| # | 不変条件 |
|---|---|
| I-1 | close 時に上書きするヘッダのバイト長は、open 時に書き込んだヘッダのバイト長と等しい |
| I-2 | ヘッダの上書き位置はファイル位置 0 である |
| I-3 | open 時点のヘッダの Duration は 0（プレースホルダ）である |
| I-4 | 出力されるすべての Cluster Timecode は t0 基準である |
| I-5 | 各チャンクの末尾 32 バイトは、次のチャンク（または close 処理）まで出力されない |

## 5. 副作用

- 出力先ファイルへの書き込みは、次の 2 種類だけである。
  - 追記（open 時のヘッダ、各チャンク）
  - 位置 0 への上書き（close 時のヘッダ）
- 位置 0 以外の既存領域への上書きは行わない。
- close 前のファイルは、ヘッダの Duration が 0 のままである。

## 6. 他ドメインへの前提・依存

- **録画元（呼び出し元ノード）**: チャンクを時系列順に 1 本のストリームとして渡すこと。
- **ストレージ／出力先**: 位置 0 へのシーク上書き（ランダムアクセス書き込み）ができること。
- **QA**: close 後のファイルで次の 2 点を検証できるように、観点を用意すること。
  - Duration が確定値になっていること
  - 先頭の Cluster Timecode が t0 基準であること

## 7. 未確定事項

| # | 未確定事項 | 影響 |
|---|---|---|
| Q1 | ヘッダの範囲（EBML Header / Segment / Info のどこまでか）と、Duration の型・バイト幅（float 4B / 8B） | I-1 を満たす実装方式 |
| Q2 | t0 の定義（録画開始時刻、ヒヤリ発生時刻からの遡り開始点、最初の Cluster の Timecode など） | 振り直し値、QA の期待値 |
| Q3 | Duration の確定方法（最終 Block の時刻、壁時計の差分など）と単位（TimecodeScale 依存） | close 時のヘッダ値 |
| Q4 | Timecode を振り直すことで EBML の可変長整数の長さが変わる場合の扱い | バイト長の保持、後続オフセット |
| Q5 | close 時の繰り越しバッファの扱い（振り直し後に追記するか、どの順序で行うか） | ファイル末尾の完全性 |
| Q6 | close せずに異常終了した場合（Duration=0 のファイル）の扱い（破棄、再生可として保存、修復など） | 録画の欠損時の挙動 |
| Q7 | 本方式がデータサイズ改善（要求 ⑤）にどう寄与するか、または別ノードで対処するか | 要求 ⑤ の達成判定 |
| Q8 | Cues（シークインデックス）と Segment サイズの扱い | 再生時のシーク可否 |
| Q9 | 繰り越しバイト長を 32 バイトとした根拠（境界をまたぐ要素の最大長との関係） | 境界処理の正しさ |

## 8. 関連 fact

- (approved / design_decision) ヘッダの扱いは次のとおりとする。
  - open 時にヘッダへ Duration=0 のプレースホルダを入れてバイト長を固定する。
  - 各チャンクは書き込み前に Cluster Timecode を t0 基準へ振り直し、末尾 32B を次のチャンクへ繰り越す。
  - クローズ時は、確定した Duration を持つ同じ長さのヘッダを位置 0 に上書きする。
